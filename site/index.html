Late booking amendments — a functional analysis

How a short-sea RoRo operator could turn four inconsistent amendment channels into one set of rules that developers can build, testers can test and support can explain.

The challenge

Tidewell Shortsea Lines (fictional) ships mostly unaccompanied trailers between Belgium, the UK and Ireland. Customers move trailers to other sailings through four channels, and each channel follows its own rules.

Portal

Stops 24 h early

After that, customers have to call. ±35% of amendments end up on the phone.

EDI

Overwrites bookings

No check on cut-off, space or dangerous goods. One customer re-sends everything, twice.

Booking desk

Rules in heads

Five different "cut-offs", an Excel per route, and exceptions nobody owns.

Terminal

Told too late

The gate shows the old sailing. ±6 wrong-sailing incidents a month.

Illustrative assumptions — not real company data.

My role in this case

This case simulates a functional analyst working with a Scrum team. Discovery, workshop decisions and UAT are fictional. I:

  • simulated interviews with booking desk, terminal operations, commercial, finance and EDI customers;
  • planned an event storming and turned its hotspots into options for the people who own each decision;
  • wrote one rule set and one decision table that every channel uses;
  • specified ten user stories with Given/When/Then criteria — the decision examples run as tests;
  • modelled the process, the amendment state machine and the logical data model;
  • described the EDI, portal and terminal interfaces, including duplicates and failures;
  • prepared refinement and UAT with developers and testers, and the handover to application support.

Event storming: where the disagreements went

Everyone described the same amendment differently. On an event-storming timeline those differences show up as red hotspots instead of disappearing into a document. The simulated outcomes record options and proposed decision owners. In real work, those owners would validate the choices.

One rule set for every channel

18 business rules, each with an owner and an example, and one decision table that the portal, EDI and the booking desk all use. The row order is a design decision: duplicates first, "loading closed" before "sailing full", the human decision last.

The 27 decision examples in the acceptance criteria run as tests against the same rule module that powers the checker.

Review: deadline, execution and delivery

At exactly T-30 new changes and approvals close. Receipt time preserves eligibility, while current time, status and capacity determine execution. Applied records the booking commit and queued notifications; delivery can fail independently.
