# Interfaces — portal API and terminal notification

> **What this is:** the functional contract between the portal / agent screen and the booking system, and the notification to the terminal. Developers own the technical API design; this page fixes the behaviour they must deliver. **Previous:** [EDI amendment](edi-amendment.md) · **Next:** [definition of ready](../07-delivery/definition-of-ready.md).

## Portal and agent screen → booking system

**Request a sailing change** — one operation for portal and agent screen (BR-17).

| Input | Mandatory | Note |
|---|---|---|
| booking number | yes | must belong to the customer (portal) or be visible to the agent |
| requested sailing | yes | same route only (BR-03) |
| idempotency key | yes | generated by the screen per click; a retry with the same key returns the first answer (BR-01 for the portal) |
| requested by | yes | user ID; channel derived from the application (PORTAL / AGENT) |

**Responses**

| Outcome | Meaning for the screen | Example body (illustrative) |
|---|---|---|
| Applied | show new sailing | `{"amendmentId":"A-77","state":"APPLIED","sailing":"S-2200","flags":["LATE_FEE"]}` |
| Pending approval | show "terminal is checking", expiry | `{"amendmentId":"A-78","state":"PENDING_APPROVAL","expiresAt":"21:30"}` |
| Rejected | show reason text; for NO_CAPACITY also the suggestion | `{"state":"REJECTED","reason":"NO_CAPACITY","suggestedSailing":"S-0600"}` |
| No change | "already on that sailing" | `{"state":"NO_CHANGE"}` |

A rejection is a normal business answer, not a technical error: the screen must show it as information, not as "something went wrong".

**Follow-up:** the screen can fetch the amendment by ID to show the final outcome of a pending request; customers also get an e-mail (AC-06.2).

## Terminal notification

| | |
|---|---|
| Trigger | Amendment applied **and** unit terminal status = GATED_IN (BR-16) — at acceptance or at approval |
| Content | unit number, booking number, previous sailing, new sailing, amendment ID, time |
| Expected effect in the TOS | gate and yard show the new sailing; loading list of the previous sailing no longer contains the unit |
| Delivery | at least once; the TOS ignores a notification with an amendment ID it already processed |
| Failure | retry; after 3 failed attempts *(illustrative)* alert to Application Support (AC-07.2, EX-6) |

**Open point for refinement:** does the TOS need the notification for units *not yet* gated in? Today it reads the booking at gate-in, so release 1 says no. Confirm with terminal IT (A-02).

## Finance (ERP)

The fee flag (BR-13) is part of the amendment data the ERP already reads for invoicing. No new interface in release 1; the ERP team adds fee code LAF to its mapping.
